# Участие в разработке

Этот документ описывает процесс подготовки изменений и pull request для Book Shelf.

## Подготовка окружения

1. Создай и активируй виртуальное окружение:

   ```bash
   python -m venv .venv
   ```

   Активация в Windows:

   ```powershell
   .venv\Scripts\activate
   ```

   Активация в Linux или macOS:

   ```bash
   source .venv/bin/activate
   ```

2. Установи зависимости:

   ```bash
   pip install -r requirements.txt
   ```

3. Создай `.env` на основе `.env.example` и укажи токен VK-бота в `BOT_TOKEN`.

4. Запусти бота:

   ```bash
   python src/main.py
   ```

Дополнительные сведения о локальном окружении находятся в [DevNotes.md](./DevNotes.md).

## Ветки

Создавай рабочую ветку от актуальной `main`. Название ветки должно соответствовать схеме:

```text
<type>/<issue-number>/<slug>
```

- `<type>` — `feature` для новой функциональности, `fix` для исправления ошибок или `chore` для технических задач.
- `<issue-number>` — номер задачи в GitHub Issues.
- `<slug>` — краткое описание строчными буквами через дефисы.

Примеры:

```text
feature/73/shorten-main-keyboard
fix/51/slow-queries
chore/102/update-dependencies
```

## Сообщения коммитов

Используй [Conventional Commits](https://www.conventionalcommits.org/ru/): по этим сообщениям Release Please определяет номер следующей версии и формирует changelog.

- `feat: добавить экспорт библиотеки` — новая функциональность, повышает minor-версию.
- `fix: исправить расчёт статистики` — исправление ошибки, повышает patch-версию.
- `docs: обновить инструкцию запуска`, `chore: обновить зависимости` — документация и технические задачи.
- `feat!: изменить формат конфигурации` — несовместимое изменение, повышает major-версию. Вместо `!` можно добавить в описание коммита `BREAKING CHANGE:`.

Область изменения можно указывать в скобках, например `fix(stats): учитывать переносы страниц`.

## Работа над изменением

- Соблюдай [CODING_STANDARDS.md](./CODING_STANDARDS.md): там описаны стиль кода, архитектурные границы, правила обработчиков и тестирования.
- Делай изменения небольшими и связанными с одной задачей.
- Добавляй или обновляй тесты при изменении поведения приложения.
- Обновляй документацию, если меняются команды бота, настройка, запуск или правила разработки.
- Не добавляй в коммит `.env`, токены, базы данных и содержимое служебных каталогов `data/`, `logs/` и `temp/`.

## Проверка изменений

Перед созданием pull request выполни все [обязательные проверки](./CODING_STANDARDS.md#обязательная-проверка-изменений). Форматирование, линтинг и тесты должны завершаться успешно.

Если изменилась только документация, достаточно проверить ссылки, форматирование Markdown и отсутствие ошибок в diff.

## Pull request

- Создавай отдельный pull request для каждой самостоятельной задачи.
- В названии кратко укажи результат изменения.
- В описании перечисли основные изменения и их назначение.
- Свяжи pull request с задачей через `Closes #<номер>`, если он полностью её закрывает, или `Related to #<номер>`, если закрывает только часть работы.
- Укажи выполненные проверки.
- Отдельно опиши миграции базы данных, изменения конфигурации и действия, необходимые при развёртывании.

Перед отправкой проверь, что в diff входят только относящиеся к задаче файлы.
