## Context

Скорость чтения вычисляется в `ReadingStatsService.avg_pages_per_day` (`src/core/services.py`): окно 30 дней захардкожено (`today - timedelta(days=29)`), начало окна не раньше `reading_start_date` книги, деление на все календарные дни окна. Без параметра её вызывают четыре потребителя: `handlers/details.py`, `flows/progress_update.py`, прогноз `predict_days_to_completion` (внутри того же сервиса), порог скачка в `core/progress_validation.py` (получает avg аргументом из прогресс-флоу). Строки «Среднее за 30 дней» захардкожены в двух форматтерах `utils/helpers.py`.

Таблицы настроек в SQLite нет (`users`, `books`, `read_stats`, `user_state`, `goals`); `user_state` семантически для состояний диалогов. Время в системе наивное локальное (серверное), бот реактивный, фоновых задач нет. Терминология зафиксирована в `CONTEXT.md`, изменения ведутся через openspec. Паттерн state-machine-меню отработан в `handlers/goal.py`, паттерн миграций в `core/migrations.py`.

## Goals / Non-Goals

**Goals:**

- Персональные настройки пользователя, первая: период скорости чтения, фиксированный набор 7 / 14 / 30, по умолчанию 30.
- Команда `/settings`: экран с текущими значениями, изменение кнопками, выход кнопкой «Назад».
- Скорость чтения считается по периоду пользователя во всех потребителях: детали книги, мини-статистика прогресса, прогноз завершения, порог скачка.
- Существующие пользователи без изменений поведения (нет строки = 30).

**Non-Goals:**

- Произвольный период (текстовый ввод числа): кнопки покрывают спрос, расширение набора значений тривиально на уровне константы.
- Другие настройки: инфраструктура (таблица, сервис, экран) готова к добавлению, каждая новая настройка это колонка + пункт экрана.
- Глобальные или групповые настройки: настройки только персональные.
- Учёт часовых поясов: отдельный issue, «день» = календарный день в локальном времени сервера.

## Decisions

1. **Настройка действует на все потребители скорости чтения**
   - Окно усреднения меняется в деталях книги, мини-статистике прогресса, прогнозе завершения и пороге скачка одновременно.
   - Альтернатива: менять только отображение. Отвергнута: «Скорость чтения» одна доменная величина; расхождение окна между экраном и валидатором даёт противоречивое поведение (экран говорит одно, подтверждение скачка требует другое).
   - Следствие принять осознанно: при периоде 7 дней avg обычно выше, порог `max(7 * avg, 10)` чувствительнее, подтверждений будет больше; при 30 как сейчас.

2. **Фиксированный набор значений 7 / 14 / 30, дефолт 30**
   - Кнопки клавиатуры, никакого текстового ввода и его валидации.
   - Альтернатива: произвольное целое вводом. Отвергнута: не запрошено, усложняет UX и валидацию.

3. **Типизированная таблица `user_settings`**
   ```sql
   CREATE TABLE IF NOT EXISTS user_settings (
       user_id TEXT PRIMARY KEY,
       reading_speed_period_days INTEGER NOT NULL
           CHECK (reading_speed_period_days IN (7, 14, 30)),
       created_at TEXT NOT NULL,
       updated_at TEXT NOT NULL,
       FOREIGN KEY (user_id) REFERENCES users (id)
   )
   ```
   - Одна строка на пользователя (`user_id` PK), upsert перезаписывает значение и `updated_at`.
   - Отсутствие строки = 30: регистрация пользователя ничего не пишет, INSERT только при первом изменении настройки. Поэтому миграция данных не нужна и поведение существующих пользователей не меняется.
   - `CHECK` защищает набор значений на уровне схемы.
   - Альтернатива A: key-value `(user_id, key, value)` по образцу `goals`. Отвергнута: разнотипные значения пришлось бы хранить в TEXT и валидировать в сервисе, строгая схема дешевле при малом числе настроек.
   - Альтернатива B: JSON в `user_state`. Отвергнута: таблица для состояний диалогов, не для настроек.
   - Pydantic-модель не заводится: сервис возвращает `int`, одна настройка.

4. **Период резолвит сам сервис статистики**
   - `ReadingStatsService.__init__` создаёт `UserSettingsRepository`; `avg_pages_per_day(book)` без изменения сигнатуры берёт период по `book.user_id`, при отсутствии строки 30.
   - Все четыре потребителя (детали, прогресс-флоу, прогноз, порог скачка через avg-аргумент) получают новое поведение одной правкой; сигнатуры и существующие тесты вызовов не ломаются.
   - Формула не меняется: `from_date = max(today - timedelta(days=period - 1), reading_start_date)`, деление на календарные дни окна.
   - Альтернатива: явный параметр `period_days` у всех вызывающих. Отвергнута: четыре точки изменения, риск забыть одну (особенно `predict_days_to_completion`, который зовёт `avg_pages_per_day` внутри сервиса).

5. **UX: state-machine по образцу `goal.py`**
   - Вход: `get_or_create_user`, состояние `{"command": "/settings", "state": "menu", "data": {"user_id": ...}}`, экран настроек с клавиатурой.
   - Кнопки текстом без payload (матчинг по `context.text.strip().lower()`, маршрутизация вторым проходом роутера по команде состояния): «7 дней», «14 дней», «30 дней», «Назад».
   - Выбор значения: применить немедленно (upsert), отправить «Период скорости чтения: N дней» с той же клавиатурой, остаться в `menu`: можно менять несколько раз подряд. Отличается от `goal.py` (там сценарий закрывается после действия), для страницы настроек это естественно.
   - «Назад»: собственная обработка в SettingsHandler, не переиспользовать `CancelHandler`: `delete_state()`, сообщение «Возврат в главное меню» с главной клавиатурой. «Операция отменена» странно для навигации, отменять тут нечего. Набранная руками «отмена» продолжает работать через `CancelHandler` как fallback.
   - Произвольный текст в `menu`: `format_invalid_input("Выбери значение из клавиатуры.")` с клавиатурой настроек, без выхода из сценария.

6. **Экран настроек**
   ```
   Настройки

   Период скорости чтения: 30 дней
   (за сколько дней считается среднее количество страниц в день)
   ```
   - Клавиатура: ряд 1 «7 дней», «14 дней», «30 дней»; ряд 2 «Назад». После выбора то же сообщение с новым значением.

7. **Интеграция в UI без алиасов**
   - `commands = ["/settings"]`, кнопка главной клавиатуры с текстом `/settings` (консистентно с остальными девятью кнопками: `/progress`, `/edit`, ...).
   - Последний ряд `main_keyboard()` становится из трёх кнопок четырёхкнопочным: `/goal`, `/stats`, `/help`, `/settings`.
   - Строка о `/settings` в `/help`.

8. **Форматтеры статистики**
   - `format_book_details` и `format_progress_stats` получают параметр `period_days: int = 30`; строка «Среднее за {period_days} дней: {avg:.2f} стр/день».
   - Вызывающие (`details.py`, `progress_update.py`) достают период через `UserSettingsService`.
   - Строки «За неделю прочитано» / «За месяц прочитано» остаются фиксированными агрегатами за 7 и 30 дней, от настройки не зависят.

9. **Гард чужого сценария**
   - В начале `handle()`: `return None`, если `context.is_active()` и `state_info["command"] != "/settings"`. Системные команды (`CancelHandler`, priority 100) перехватывают как обычно.

## Risks / Trade-offs

- **[Чувствительность скачка]** При периоде 7 дней порог `max(7 * avg, 10)` ниже (avg за активную неделю выше), подтверждения подозрительных обновлений будут чаще. Принято: это следствие выбора пользователя, поведение честное и предсказуемое.
- **[CHECK при расширении набора]** SQLite не умеет менять CHECK: добавление значения (например, 21) потребует миграции с пересозданием таблицы. Альтернатива без CHECK (валидация только в сервисе) отвергнута ради защиты на уровне схемы; расширение редкое.
- **[4 кнопки в ряд]** Подписи короткие (`/goal`, `/stats`, `/help`, `/settings`), VK рендерит четыре кнопки в ряд без обрезки.
- **[Нет произвольного периода]** Кому-то захочется 21 или 60. Расширение: значение в `READING_SPEED_PERIODS`, кнопка, миграция таблицы. Отложено.

## Migration Plan

- Таблица `user_settings` создаётся в `_create_tables` (`CREATE TABLE IF NOT EXISTS`): существующие базы получают её при старте, новых записей не появляется, все читают дефолт 30.
- Записей в `core/migrations.py` нет: данные не переносятся и не меняются.
- Откат: код без таблицы работает (все пути дают дефолт 30); при необходимости очистки вручную `DROP TABLE user_settings`.
