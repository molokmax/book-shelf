# Design

## Context

Дневная цель уже хранится в `goals` и содержит текущие `target` и `created_at`; повторная установка через UPSERT сохраняет `created_at`, а отключение удаляет строку. Выполнение цели вычисляется из `read_stats`, где положительные дельты прогресса привязаны к `user_id` и naive local `read_date`. Истории прежних значений цели и отдельных фактов её выполнения нет.

`GoalService` уже предоставляет прогресс текущего дня, `/goal` использует `GoalStatus`, а `ProgressUpdateFlow._format_goal_progress` отдельно определяет пересечение порога. Календарный день во всей функциональности цели соответствует локальному времени сервера. Требования зафиксированы в delta specs `reading-streaks` и `daily-reading-goal`.

## Goals / Non-Goals

**Goals:**

- Вычислять страйк детерминированно за один запрос с дневной агрегацией и обходом только последней серии.
- Использовать одну реализацию расчёта для `/goal` и `/progress` и один форматтер пользовательской строки.
- Оставить точку внедрения времени для тестов границ дней.
- Поддержать существующие базы без переноса или изменения пользовательских данных.

**Non-Goals:**

- Не хранить историю значений цели, ежедневные снимки выполнения или отдельный счётчик страйка.
- Не исправлять исторические пробелы в `read_stats` и не менять существующую семантику откатов прогресса.
- Не добавлять планировщик, пользовательские часовые пояса, рекорды и другую геймификацию.

## Decisions

### 1. Дневные суммы получаются одним агрегированным запросом

В `ReadStatsRepository` добавляется выборка `user_id → {date: pages}` за полуинтервал `[start_of_creation_day; start_of_tomorrow)`. SQL группирует записи по `date(read_date)` и суммирует `pages_read`; фильтр по `user_id` автоматически исключает строки с `NULL`. Границы `read_date >= ? AND read_date < ?` передаются как `YYYY-MM-DD`: так date-only и naive ISO datetime корректно сравниваются с началом дня и исключаются на следующую дату. Преобразование `date(read_date)` поддерживает оба уже используемых формата при группировке.

Альтернатива — вызывать существующий `fetch_pages_by_user` для каждого дня. Она отвергнута: количество запросов росло бы от длины истории и создавало бы N+1 даже при коротком страйке после длинной серии пропусков.

### 2. Расчёт находится в `GoalService`

Добавляется `get_current_streak(user_id, now=None) -> int | None`: без текущей цели возвращается `None`. Для текущей цели нижней границей истории служит начало календарного дня `goal.created_at`, а не само время создания.

Алгоритм после получения дневных сумм:

1. Если сегодняшняя сумма достигает `goal.target`, начать с сегодняшней даты; иначе — со вчерашней.
2. Если начальный день не выполнен, вернуть `0`.
3. Идти назад по календарным датам, пока сумма каждого дня достигает текущего `target`, но не раньше даты создания цели.
4. Вернуть количество пройденных дней.

Отсутствующая дата имеет нулевую сумму и разрывает серию. Будущие записи исключаются верхней границей запроса. Изменение `target` автоматически даёт пересчёт всей истории, а удаление цели делает результат `None`; отдельная синхронизация не нужна.

Альтернатива — отдельная таблица ежедневных выполнений. Она отвергнута: потребовала бы backfill, истории значений цели и согласования записей при изменении цели, а также не давала бы преимуществ при текущих объёмах личной статистики.

### 3. `GoalStatus` содержит уже вычисленный страйк

В `GoalStatus` добавляется поле `streak: int`. `get_goal_status` получает необязательный `now`, передаёт его в расчёт страниц и страйка и заполняет поле; при отсутствии цели по-прежнему возвращается `None`. Внутренний расчёт принимает уже загруженную цель, чтобы экран `/goal` не запрашивал её повторно.

`ProgressUpdateFlow` сохраняет текущую проверку пересечения порога и запрашивает `get_current_streak` только в ветке поздравления, после записи новой статистики и внутри существующей обработки ошибок цели. Поэтому обычные обновления прогресса не читают всю историю цели. Повторный запрос цели в этом редком пути проще отдельного необязательного режима `get_goal_status`.

### 4. Одна функция форматирует строку страйка

В `utils/helpers.py` добавляется форматтер `🔥 Страйк: N ...` с русскими формами `день`, `дня`, `дней`, включая исключения 11–14 и повторение правил для следующих сотен.

- `GoalHandler._format_menu_text` добавляет строку после результата текущего дня и перед `Выбери действие:`.
- Ветка поздравления `ProgressUpdateFlow` добавляет строку через `\n` сразу после существующего 🎉-текста внутри того же блока.
- Обычная строка цели, поведение клавиатур, состояния сценариев и подавление мотивационной фразы при поздравлении не меняются.

Альтернатива — дублировать склонение в обработчике и flow. Она отвергнута из-за риска разных форматов в двух точках отображения.

### 5. Добавляется только индекс

В `core/migrations.py` добавляется идемпотентная миграция с `CREATE INDEX IF NOT EXISTS` для `read_stats(user_id, read_date)`. Она вызывается в `Database.__init__` сразу после `add_read_stats_user_id`: так индекс создаётся и для новых баз, и для старых баз, где колонка `user_id` появляется только миграцией. Таблицы и данные не изменяются.

Индекс поддерживает фильтр пользователя и диапазона дат. Группировка всей истории остаётся пропорциональной количеству записей текущей цели, но не требует дополнительного состояния и обычно затрагивает небольшой личный журнал.

## Risks / Trade-offs

- **[Текущая цель применяется к прошлому]** Изменение `target` может неожиданно увеличить или обнулить серию. → Поведение явно закреплено в требованиях и тестах; это осознанная замена отсутствующей истории целей.
- **[Неполная статистика]** Подавленные ошибки записи и старые строки с `user_id IS NULL` могут занижать страйк. → Используется тот же источник истины, что и для выполнения дневной цели; восстановление истории не входит в задачу.
- **[Рост истории]** Даже короткий страйк требует агрегировать записи от создания цели. → Один SQL-запрос и индекс вместо N+1; денормализацию рассматривать только после измерения реальной нагрузки.
- **[Серверная полночь]** Граница серии может не совпадать с календарным днём пользователя. → Используется существующее определение дневной цели; пользовательский часовой пояс остаётся отдельной задачей.
- **[Смешанные форматы дат]** Нестандартные значения `read_date`, записанные в обход основного пути, могут группироваться некорректно. → Поддерживаются оба фактически используемых ISO-формата; новая валидация исторических данных не добавляется.

## Migration Plan

1. При старте новая миграция идемпотентно создаёт индекс `read_stats(user_id, read_date)` после миграции колонки `user_id` для новых и существующих баз.
2. Backfill не требуется: первый запрос страйка использует уже сохранённые `goals.created_at`, `goals.target` и `read_stats`.
3. Откат кода не требует удаления индекса: прежняя версия может оставить его без изменения поведения. Таблицы для отката отсутствуют.
