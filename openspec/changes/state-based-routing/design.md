## Context

Сейчас `CommandRouter.route()` вызывает `handler.can_handle(context.command)` для каждого обработчика. Если пользователь находится в активном стейте (например, вводит название книги для `/add`) и ввёл произвольный текст, `can_handle` возвращает `False` для всех обработчиков, и роутер не направляет сообщение. После этого управление падает в устаревший fallback-диспатчинг в `bot.py`, который дублирует логику обработчиков.

Состояние пользователя хранится в SQLite (`ActiveStateStorage` → `UserStateRepository`) как `{"command": "...", "state": "...", "data": {...}}`. Поле `command` указывает, к какой команде относится активный стейт. `BotContext` предоставляет доступ к этому через `context.is_active()` и `context.command_state`.

## Goals / Non-Goals

**Goals:**
- Сообщение должно направляться обработчику, если введённая команда совпадает с `commands` обработчика ИЛИ если активный стейт пользователя указывает на команду этого обработчика
- Удалить дублирующий fallback-диспатчинг из `bot.py`
- Минимальные изменения в API обработчиков — предпочтительно без изменения `can_handle()`

**Non-Goals:**
- Не менять логику внутри `handle()` — обработчики уже корректно обрабатывают и entry point, и step-продолжения
- Не менять механизм хранения стейта
- Не добавлять новые обработчики

## Decisions

1. **Модификация `route()` вместо `can_handle()`**
   - Альтернатива A: расширить `can_handle(command, context)` — меняет сигнатуру базового класса и всех наследников
   - Альтернатива B: после цикла проверки `can_handle(context.command)` сделать второй проход с `context.command_state` при активном стейте — не меняет API, простое изменение
   - **Решение**: Вариант B. После того как ни один обработчик не совпал по `context.command`, и если `context.is_active()`, повторяем поиск по `context.command_state`. Это минимальное изменение.

2. **Удаление fallback-диспатчинга из `bot.py`**
   - После того как роутер научился обрабатывать стейт, код в `handle_event()` после вызова `router.route()` становится мёртвым
   - **Решение**: Удалить блок-диспатчинг (команды `/list`, `/edit`, `/details` и их step-варианты) из `handle_event()`. Если `router.route()` вернул `None` — просто логируем и ничего не делаем.

## Risks / Trade-offs

- **[Усложнение при добавлении новых обработчиков]** Новые обработчики с многошаговым флоу должны правильно устанавливать стейт с `command`, чтобы роутинг работал. → Это уже существующее требование, не меняется.
- **[Конфликт с CancelHandler]** `CancelHandler` имеет приоритет 100 и в его `commands` есть `/cancel`, `cancel`, `отмена`. Если пользователь вводит `отмена` во время активного стейта `/add`, он должен попасть в `CancelHandler`. → Это работает и сейчас, т.к. `CancelHandler` имеет более высокий приоритет (100 vs 10).
