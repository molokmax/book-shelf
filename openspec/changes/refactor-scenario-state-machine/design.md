## Context

Сейчас путь сообщения такой: `handle_event` → `BotContext` → `CommandRouter.route` (два прохода: по введённой команде, затем по `state["command"]`) → `handler.handle(context)`. Стейт хранится в `user_state` как `{"command", "state", "data"}` через `ActiveStateStorage`; `BotContext.send_message` ведёт цепочку промежуточных сообщений (`message_chain`): удаляет предыдущий промпт сценария и запоминает id нового, пока стейт активен.

Семь многошаговых хендлеров реализуют одинаковый каркас по-разному. Эталон гарда из AGENTS.md (`return None` при чужом сценарии) соблюдён только в `progress.py`, `goal.py`, `settings.py`, `more.py`; `edit.py` и `details.py` возвращают `True` (сообщение теряется), `list.py` использует `getattr(f"_handle_{state}")` и падает на чужом стейте, `add.py` и `start.py` чужой стейт перетирают или оставляют висеть.

Флоу `TagEditingFlow`, `BookSelectionFlow`, `ProgressUpdateFlow` уже работают как под-сценарии: принимают `state_info`, пишут `state`, вызывают колбэк владельца. Их контракт менять не требуется.

Ограничения: состояние должно оставаться сериализуемым в SQLite (никаких замыканий и генераторов), тексты и клавиатуры не меняются, `pytest` и линтеры зелёные на каждом шаге.

## Goals / Non-Goals

**Goals:**

- Один каркас сценария: вход, диспетчеризация шага, переход, финал, сброс — без копипаста в хендлерах.
- Единая и централизованная политика при активном чужом сценарии, без потери сообщений и без `AttributeError`.
- Явные имена шагов (`StrEnum`), один источник истины для общих шагов под-сценариев.
- Единое поведение при неизвестном состоянии и при повторном вводе своей команды.
- Сохранить формат стейта, тексты, клавиатуры и порядок шагов; миграция данных не нужна.

**Non-Goals:**

- Дедупликация выбора книги `edit`/`details`/`list` через `BookSelectionFlow` (TODO #42) — отдельная задача.
- Смена контракта флоу (колбэки остаются).
- Типизация `data` (pydantic-модели в стейте).
- Вложенные сценарии и стек возвратов.
- Изменение роутера, приоритетов и состава команд.
- Новые шаги, тексты, клавиатуры.

## Decisions

1. **Гибрид: `ScenarioHandler` с методами-шагами и явным возвратом следующего состояния**
   - Шаг объявляется методом `step_<state>(context, state_info) -> str | None`; `None` означает «остаться в текущем шаге» (ошибка валидации), значение — имя следующего шага, по которому базовый класс вызывает `goto`.
   - `state_info` передаётся целиком (а не только `data`), потому что шаги делегируют во флоу, которым нужны и `state`, и `data`; вызывать `context.get_state()` заново не требуется.
   - Промпт шага — необязательный метод `render_<state>(context, state_info)`, который `goto` вызывает после записи состояния. Шаг, в который вход выполняет флоу (`selecting_tags`), рендер не объявляет.
   - Полнота покрытия проверяется в `__init_subclass__`: для каждого значения `states` (StrEnum сценария) обязан существовать `step_<value>`, иначе `TypeError` на импорте. Это закрывает слабое место текущего `getattr(f"_handle_{state}")` в `list.py`, где отсутствие метода выясняется только в рантайме.
   - Альтернатива A: реестр `dict[str, Step]` с dataclass `Step(enter, handle)` — функции-шаги вызываются как несвязанные методы, шумно и нетипично для проекта.
   - Альтернатива B: полноценные классы состояний с `enter/handle` — граф нагляднее, но десятки мелких классов в 7 сценариях и неудобная стыковка с флоу.
   - Альтернатива C: декларативные переходы `(from, event, guard, to)` — сильна для структурированных событий, а здесь половина шагов это свободный текст; на каждый шаг 2–3 записи с guard'ами, читается хуже `if`.
   - Следствие: имена методов выводятся из значений enum; переименование шага = значение enum + имя метода. Гарантия — проверка на импорте и тест-инвентарь состояний.

2. **Владение сценарием — `state["command"]`, без миграции**
   - У `ScenarioHandler` добавляется `scenario_command`; инвариант: это `commands[0]` — каноническая команда, которая пишется в стейт. У одношаговых хендлеров `scenario_command = None`.
   - Новое поле `scenario` в стейте не вводится: значения `command` уже канонические (`/add`, `/progress`), а миграция и фолбэк для активных пользователей — лишний риск.
   - Альтернатива: отдельное поле `scenario`. Отвергнута: выгода только семантическая, цена — миграция `user_state` и двойное чтение на переходный период.
   - Тест: `scenario_command in commands` и начинается с `/` у каждого сценарного хендлера.

3. **Гард чужого сценария — в шаблонном методе `handle()`**
   ```python
   def handle(self, context):
       if context.is_active() and not self.is_system:
           owner = context.command_state
           if owner and owner != self.scenario_command:
               self.reject_foreign_scenario(context)
               return True
       return self._handle(context)
   ```
   - Отказ отправляется напрямую через `context.api.messages.send` без клавиатуры, а не через `context.send_message`: иначе `message_chain` удалит текущий промпт активного сценария, и пользователь останется в сценарии без вопроса. Побочный эффект: в чате видны промпт и сообщение об отказе; принято.
   - `is_system = True` только у `/start` и `/cancel`. `/start` в `_handle` удаляет стейт после отправки приветствия — это исключение из правила блокировки; `/cancel` ведёт себя как раньше.
   - Если состояние есть, но `command` пуст (устаревший или битый стейт), гард пропускает сообщение: сценарный хендлер уйдёт в `reset_unknown_state`, одношаговый выполнится. Зависания нет: `/cancel` и `/start` доступны всегда.
   - Отказ в роутере не реализуется: роутер остаётся про маршрутизацию, а текст и клавиатура — про UI сценариев; второй проход роутера по-прежнему нужен, чтобы шаги получали свободный текст.

4. **Повторный ввод команды сценария — перезапуск с начала**
   - Если активен сценарий этой же команды и сообщение является командой (payload-команда или текст, начинающийся с `/`) и она входит в `commands` хендлера, — стейт удаляется и вызывается `start`.
   - Алиасы без слэша (`add`, `прогресс`, `цель`) перезапуском не считаются и обрабатываются как ввод шага, как сейчас.
   - Альтернатива «блокировать с отдельным текстом» отвергнута: пользователь с клавиатуры видит ту же команду и ожидает её действие; перезапуск безопаснее, чем сохранение `/add` в качестве названия книги.

5. **Неизвестное состояние → единый сброс**
   - `reset_unknown_state`: финальное сообщение «⚠️ Не удалось продолжить сценарий. Начни заново: <команда>» с `main_keyboard()`, затем `delete_state`.
   - Сейчас `/add` сбрасывает с таким сообщением, остальные молча игнорируют; унификация убирает «немой» сценарий.

6. **`goto` — единственная точка смены шага**
   - `goto(context, state, state_info)` обновляет `state` и `command` в переданном стейте, сохраняет через `context.set_state` и вызывает `render_<state>`. Для входа в сценарий `begin(context, state, data)` создаёт новый `{command, state, data}` и вызывает `goto`.
   - Разделение `begin` и `goto` убирает двусмысленность «третий аргумент — это данные или стейт?»: данные нового сценария можно потерять, если передать их в `goto` вместо `state_info`. `start` по умолчанию вызывает `begin(initial_state)`.
   - Убирает разнобой «`set_state` до `send_message`» и «`set_state` после», из-за которого в хендлерах появлялись повторные `get_state()` и ручные копии стейта. Шаги, которые делегируют во флоу, состояние сохраняют сами (флоу), каркас их не перезаписывает.
   - `data` остаётся `dict`; типизация — non-goal.

7. **Финал централизован**
   - `finish(context, message, keyboard=None)`: `context.send_message(...)` → `context.delete_state()`. Порядок обязателен и закрепляется тестом: `send_message` удаляет висящий промпт, а id финального сообщения стирается вместе со стейтом и не удаляется следующими сообщениями.
   - Комментарий-объяснение остаётся только в базовом классе, а не в восьми местах.

8. **Имена шагов — `StrEnum` в `src/vk_bot/states.py`**
   - Значения совпадают с текущими строками (`"waiting_for_title"`, `"selecting_tags"`, …), поэтому данные в `user_state` совместимы и миграция не нужна.
   - Общие шаги под-сценариев — отдельные перечисления: `SelectionState`, `TagState`, `ProgressState`; сценарные (`AddState`, `EditState`, `DetailsState`, `ListState`, `ProgressScenarioState`, `GoalState`, `SettingsState`) содержат все шаги своего сценария, включая общие, с теми же значениями.
   - Флоу используют константы из `states.py` вместо литералов; значения и логика не меняются. Тест-инвентарь проверяет, что общие состояния во флоу и в перечислениях сценариев совпадают.
   - Альтернатива «строковые константы» отвергнута: нет проверки полноты и общего типа; альтернатива «своё поле `scenario`» — см. п. 2.

9. **Флоу сохраняют контракт**
   - `start` вызывается из шага сценария и получает `state_info`; `handle` обрабатывает ввод; колбэк (`on_done` / `on_selected`) выполняет финал через `self.finish(...)`.
   - `ProgressUpdateFlow` завершает сценарий сам (`send_message` → `delete_state`), как и раньше: владельца флоу не знает, а выносить финал в колбэк — значит менять контракт флоу (non-goal).
   - Владелец (`command`) не меняется, поэтому второй проход роутера продолжает находить сценарий по шагу флоу.

10. **Одношаговые команды тоже блокируются**
    - `/help`, `/stats`, `/export`, `/more`, `/back` при чужом активном сценарии получают тот же отказ. Это меняет текущее поведение `help`/`stats`/`export` (выполнялись поверх сценария) и `more`/`back` (возвращали `None`, сообщение уходило в сценарий).
    - Причина: единое правило проще объяснить и невозможно «случайно» выполнить экспорт посреди ввода названия книги.

11. **Роутер и `message_chain` без изменений**
    - `CommandRouter`, `BotContext`, `ActiveStateStorage`, `message_chain` не меняются. Риск регрессии в маршрутизации минимален, тесты `tests/test_command_router.py` остаются валидными.

## Risks / Trade-offs

- **[Блокировка одношаговых команд]** `/help`, `/stats`, `/export` перестают работать во время сценария. Принято осознанно: пользователь получает понятный отказ и кнопку «Отмена».
- **[Два сообщения при отказе]** Промпт сценария не удаляется, поэтому в чате видны промпт и отказ. Альтернатива (удалить промпт) оставила бы активный сценарий без вопроса — хуже.
- **[Проверка шагов на импорте]** `__init_subclass__` роняет импорт при забытом `step_*`; это громкий и ранний отказ, но требует зелёного `pytest` до мержа.
- **[Соглашение об именах]** `step_<state>` — «магия» в именах методов. Компенсация: значения задаёт enum, полнота проверяется на импорте, отдельный тест инвентаря.
- **[Поведение `/start`]** Исключение для `/start` (сброс сценария) отличается от общей блокировки; зафиксировано в спеке и тестах.
- **[Стейты в проде]** У пользователей могут быть активные сценарии. Значения шагов и `command` не меняются, поэтому после деплоя они продолжаются штатно; откат кода тоже безопасен.
- **[Массовая правка тестов]** Тесты, ожидающие `None` от `more`/`settings`/`goal`/`progress` при чужом сценарии, меняют ожидание на отказ. Правки механические.

## Migration Plan

- Данные не затрагиваются: новых таблиц, колонок и миграций нет; формат `user_state` прежний, значения состояний прежние.
- Порядок работ (после каждого шага зелёные `pytest` и линтеры): каркас и `states.py` → гард и одношаговые → сценарии по одному (`/goal`, `/settings`, `/list`, `/add`, `/details`, `/edit`, `/progress`) → флоу на константы → документация.
- Откат: revert коммитов. Активные сценарии переживают откат, так как формат и значения стейта не менялись.
