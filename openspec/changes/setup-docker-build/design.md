## Context

Бот запускается как долгоживущий процесс: `python src/main.py` поднимает VK Long Poll цикл с автоматическим переподключением (`src/vk_bot/bot.py`). HTTP-эндпоинтов нет. Данные хранятся в SQLite (`data/database.db`, путь относительно CWD), логи пишутся и в stdout, и в `logs/app.log` (`src/utils/logger.py`). Конфигурация читается из переменных окружения: `BOT_TOKEN` (обязателен), `DATA_DIR`, `TEMP_DIR`, `DEBUG` (`src/utils/config.py`), плюс `load_dotenv()` ищет `.env` в CWD.

Текущий деплой: systemd-юнит `deploy/book-shelf.service` на сервере с ручным venv и установкой полного `requirements.txt` (включая dev-пакеты: black, flake8, pytest, mypy и т.д.). Сборки как таковой нет. Для релизов нужен версионированный артефакт в registry.

Ограничения: Windows-машина разработчика, сборка образа происходит на Linux-сервере или в CI; python-версия проекта зафиксирована как 3.11 (black `target-version = ["py311"]`).

## Goals / Non-Goals

**Goals:**

- Воспроизводимая сборка Docker-образа одной командой из корня репозитория.
- Минимальный runtime-образ: только prod-зависимости, без dev-пакетов и pip в финальном слое.
- Запуск от непривилегированного пользователя.
- Сохранение SQLite-данных между пересозданиями контейнера через том.
- Публикация образа в Docker Hub по пушу тега `v*` через GitHub Actions.
- Плавный переход с systemd-деплоя: данные переносятся без потерь, откат задокументирован.

**Non-Goals:**

- Мультиархитектурная сборка (linux/arm64) — публикуется только `linux/amd64`.
- Переписывание systemd-деплоя: `deploy/` остаётся рабочим вариантом.
- Изменение кода `src/` и структуры конфигурации.
- Горизонтальное масштабирование: Long Poll не рассчитан на несколько реплик.

## Decisions

### 1. Многоступенчатая сборка на `python:3.11-slim`

`builder`-стадия создаёт venv (`/opt/venv`) и ставит `requirements-prod.txt`; `runtime`-стадия копирует venv целиком и `src/`, без pip и компилятора. Итоговый слой содержит только интерпретатор, venv и код.

Альтернативы: `python:3.11-alpine` (меньше, но musl; выгода несущественна для pure-Python зависимостей, а slim надёжнее), одностадийная сборка (проще, но pip и его кэш остаются в образе).

### 2. Отдельный `requirements-prod.txt`

Runtime-зависимости по факту используются только три: `vk_api`, `requests`, `python-dotenv` (проверено по импортам `src/`; pydantic/httpx в коде не встречаются). Версии фиксируются по текущему `requirements.txt`: `vk_api==11.10.0`, `requests==2.32.5`, `python-dotenv==1.2.1`. Транзитивные зависимости ставит pip.

Альтернатива: ставить в образ полный `requirements.txt` — просто, но тянет dev-пакеты (black, mypy, pytest и др.) в прод-образ. Отвергнуто.

### 3. Непривилегированный пользователь и права на том

В `runtime`-стадии создаётся системный пользователь `book-shelf` (uid 10001, без шелла). `WORKDIR /app`, каталоги `/app/data` и `/app/temp` создаются в образе с владельцем `book-shelf`. Named volume при первом монтировании наследует владельца каталога из образа, поэтому права на SQLite решаются без bind mount и подгонки uid под хост.

Альтернатива: bind mount `./data:/app/data` — проще для существующего сервера, но ломается при несовпадении uid хоста и контейнера (SQLite не сможет писать). Отвергнуто в пользу named volume + миграция через `docker cp`.

### 4. Часовой пояс в образе

`ENV TZ=Europe/Moscow` + пакет `tzdata` (в slim его нет). Статистика чтения использует локальные даты, без tzdata расчёты «за сегодня/неделю» уплывут на UTC.

### 5. `docker-compose.yml` как основной способ запуска

Compose-сервис `book-shelf`: `build: .`, `env_file: .env` (токен не светится в командной строке), named volume `book-shelf-data:/app/data`, `restart: unless-stopped`. Это покрывает и локальный запуск, и сервер.

### 6. Без HEALTHCHECK

HTTP-эндпоинтов нет, проверять можно только живость процесса, а её уже покрывает `restart: unless-stopped` (краш → перезапуск). pgrep-хелсчек не добавляет ценности. Сознательно опущено.

### 7. Логи: stdout + файл внутри контейнера

`logger.py` уже дублирует в консоль и в `logs/app.log`. В контейнере консольный вывод доступен через `docker compose logs`, файловые логи живут в контейнере (эфемерны) — каталог `logs/` создаётся самим приложением, монтировать его не требуется.

### 8. Публикация образа через GitHub Actions в Docker Hub

Workflow `.github/workflows/docker-publish.yml` запускается на `push` тегов `v*`. Шаги: checkout, `docker/setup-buildx-action`, `docker/login-action` с секретами `DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN`, `docker/metadata-action` для генерации тегов из semver (`{{version}}`, `{{major}}.{{minor}}`, `latest`), `docker/build-push-action` с `push: true` и кэшем `type=gha`. Образ публикуется как `<DOCKERHUB_USERNAME>/book-shelf`.

Тег `latest` вешается только на стабильные релизы: `type=raw,value=latest,enable=${{ !contains(github.ref_name, '-') }}`, чтобы pre-release (`v1.0.0-rc.1`) не перетирал `latest`.

Альтернативы: GHCR (использует встроенный `GITHUB_TOKEN`, секреты не нужны) — отвергнут, так как выбран Docker Hub; ручная сборка на сервере — не даёт версионированных артефактов и воспроизводимости.

## Risks / Trade-offs

- [SQLite и несколько контейнеров: два контейнера, пишущие в одну БД, повредят данные; две реплики Long Poll получат дубли событий] → в compose не задаём реплики; запускается ровно один контейнер.
- [Потеря данных при миграции] → инструкция: остановить systemd-юнит до первого старта контейнера, перенести `database.db` через `docker cp`, откат — обратный `docker cp` в `./data/`.
- [Попадание `.env` или БД в слой образа] → `.dockerignore` исключает `.env`, `data/`, `logs/`, `temp/`; это же ускоряет контекст сборки.
- [Дрейф версий зависимостей] → `requirements-prod.txt` закрепляет те же версии, что в `requirements.txt`; обновление пакетов остаётся ручным шагом в обоих файлах.
- [Компрометация токена Docker Hub] → используется access token (не пароль) с минимально нужными правами, хранится в секретах GitHub; при подозрении — ротация.
- [Pre-release перетирает `latest`] → тег `latest` включается только когда имя тега не содержит дефис (см. решение 8).
- [Рассинхрон версии образа и кода] → теги образа генерируются из git-тега, который является единственным источником версии релиза.

## Migration Plan

1. На сервере: `docker build -t book-shelf .` (или `docker compose build`).
2. `systemctl --user stop book-shelf` — остановить текущий деплой, чтобы БД не писалась параллельно.
3. `docker compose up -d` — первый старт создаёт пустую БД в томе.
4. Перенести данные: `docker cp data/database.db book-shelf:/app/data/database.db` (при запущенном контейнере) и `docker compose restart`.
5. Проверка: `docker compose logs -f` — сообщение «Бот запущен и ожидает сообщений».

Rollback: `docker compose down` (том сохраняется), вернуть БД на хост (`docker cp` в обратную сторону, если контейнер успел записать новые данные), `systemctl --user start book-shelf`.

Релиз: `git tag vX.Y.Z && git push origin vX.Y.Z` — workflow публикует образ в Docker Hub; на сервере обновление через образ (`docker pull` + перезапуск) либо пересборку из тега.

## Open Questions

- Нужны ли мультиархитектурные образы (linux/arm64) — зависит от архитектуры сервера, на который деплоится.
- Уместно ли в будущем вынести `logs/` в том — зависит от того, понадобится ли файловый доступ к логам вне контейнера.
