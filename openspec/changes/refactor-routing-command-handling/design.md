## Context

Роутинг и обработка команд в боте сейчас распределены по разрозненным функциям без централизованного управления. При добавлении новых команд приходится править множество файлов‑обработчиков, а отсутствие приоритетов и явного состояния приводит к конфликтам и трудно тестируемому коду.

В `proposal.md` описана необходимость рефакторинга в виде новой возможности **routing-refactor**, которая подразумевает централизованный роутер, базовый класс обработчиков, хранение пользовательского состояния в SQLite и контекст‑объект для доступа к сервисам.

## Goals / Non-Goals

**Goals:**
- Вынести логику роутинга в единственный класс `CommandRouter`.
- Ввести базовый класс `AbstractCommandHandler` с поддержкой списка команд, приоритета и методами `can_handle`/`handle`.
- Реализовать состояние пользователя в SQLite через `UserStateRepository`.
- Обновить существующие обработчики (`add`, `edit`, `list` и др.) под новую архитектуру без изменения публичного API бота.

**Non-Goals:**
- Не менять внешние API Telegram/VK.
- Не внедрять новые внешние зависимости.
- Не писать UI‑клавиатуры заново – оставить текущие клавиатуры из `src/vk_bot/keyboards.py`.

## Decisions

1. **Using a singleton `CommandRouter`** – упрощает интеграцию в `bot.py` и гарантирует один источник правды о порядке обработки.
2. **Priorities as integer (higher = later)** – позволяет задать базовый уровень (0) для «универсальных» обработчиков и более высокий для специфичных.
3. **SQLite for user state** – уже используется база `data/database.db` для основной модели; будем хранить отдельную таблицу `user_state(user_id TEXT PRIMARY KEY, json TEXT)`.
4. **Synchronous vs Async** – весь код останется синхронным, как в текущем проекте, чтобы не менять цикл обработки сообщений.

## Risks / Trade-offs

- **Риск:** переход к новому роутеру может нарушить текущие обработчики; **смягчение:** реализовать обратную совместимость – старый роутинг будет работать как «fallback» с самым низким приоритетом.
- **Риск:** добавление SQLite‑хранилища может вызвать блокировки при одновременных запросах; **смягчение:** использовать `SELECT … FOR UPDATE` (или транзакции) и ограничить частоту записи.
- **Риск:** увеличение количества файлов усложнит поддержку; **смягчение:** чётко документировать структуру и добавить тесты для роутера и базового обработчика.

## Migration Plan

1. Добавить миграцию `user_state` в `src/core/database.py` (таблица `user_state`).
2. Реализовать `UserStateRepository` с методами `get_state(user_id)`, `save_state(user_id, state_dict)`.
3. Переписать один обработчик (`add.py`) как пример, проверить через тесты.
4. Поэтапно мигрировать остальные обработчики, оставляя старый роутинг как fallback.
5. Обновить `src/vk_bot/bot.py` – инициализировать `CommandRouter`.
7. Запускать тестовый цикл и убедиться, что все текущие тесты проходят.
