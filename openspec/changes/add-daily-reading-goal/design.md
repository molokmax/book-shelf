## Context

Бот накапливает статистику чтения: при каждом положительном изменении прогресса `BookService.update_book_progress` пишет в `read_stats(book_id, pages_read, read_date)` запись о прочитанных за раз страницах. «Сколько прочитано за сегодня» вычислимо как сумма таких записей, но: в `read_stats` нет `user_id` (только join через `books`, и при удалении книги её записи выпадают из суммы), а настройки цели хранить негде.

Время в системе везде наивное локальное (серверное), бот чисто реактивный (longpoll), фоновых задач нет. Терминология проекта зафиксирована в `CONTEXT.md`, изменения ведутся через openspec.

## Goals / Non-Goals

**Goals:**

- Дневная цель «N страниц в день» на пользователя (одна, по всем книгам суммарно).
- Настройка, просмотр и отключение цели через команду `/goal`.
- Отображение прогресса цели в сообщении об обновлении прогресса и поздравление ровно в момент выполнения.
- Готовность схемы данных к будущим типам целей и страйкам (без переезда данных).

**Non-Goals:**

- Долгосрочные цели («книга в месяц») — отдельная работа.
- Ачивки и страйки — используют функциональность целей позже.
- Напоминания и фоновая рассылка.
- Учёт часового пояса пользователя — заведён отдельный issue; «день» = календарный день в локальном времени сервера.
- Цели на отдельную книгу.

## Decisions

1. **Одна глобальная дневная цель на пользователя**
   - Альтернатива: цель на книгу. Отвергнута: сложный UX (настройка в каждой книге), не запрошена в issue. При появлении других типов целей меню `/goal` получит шаг выбора цели, а схема хранения это уже поддерживает.

2. **День = календарный день в локальном времени сервера**
   - Альтернатива: таймзона пользователя из VK API (`users.get` → `timezone`). Отвергнута сейчас: единообразно с остальным кодом (`datetime.now()`), проще тесты. Ограничение зафиксировано отдельным issue про часовые пояса.

3. **Хранение цели в новой таблице `goals`**
   ```sql
   CREATE TABLE IF NOT EXISTS goals (
       id TEXT PRIMARY KEY,
       user_id TEXT NOT NULL,
       kind TEXT NOT NULL,          -- сейчас только 'daily_pages'
       target INTEGER NOT NULL,     -- страниц в день
       created_at TEXT NOT NULL,
       updated_at TEXT NOT NULL,
       UNIQUE(user_id, kind),
       FOREIGN KEY (user_id) REFERENCES users (id)
   )
   ```
   - Альтернатива A: колонка `daily_goal_pages` в `users` — минимально, но второй тип цели потребует новой миграции.
   - Альтернатива B: JSON в `user_state` — таблица семантически для состояний диалогов, не для настроек.
   - Решение: таблица `goals` с `kind`; страйки и долгосрочные цели лягут без переезда.

4. **`user_id` в `read_stats` + миграция**
   - `ALTER TABLE read_stats ADD COLUMN user_id TEXT`; заливка `UPDATE read_stats SET user_id = (SELECT user_id FROM books WHERE books.id = read_stats.book_id)` для строк с NULL.
   - Записи книг, удалённых до миграции, останутся с `user_id = NULL` и не попадут в сумму дня — потеря приемлема (только давно удалённые книги).
   - Альтернатива: агрегировать через JOIN `books`. Отвергнута: статистика удалённой книги выпадала бы из суммы задним числом, запрос дороже.
   - Счётчик дня = `SUM(pages_read) FROM read_stats WHERE user_id = ? AND read_date >= начало_дня`. Откат прогресса счётчик не уменьшает (записи только по положительной дельте) — существующая семантика статистики, принимается как есть.
   - Страницы, прочитанные сегодня до установки цели, учитываются: цель — про день в целом.

5. **Выполнение цели вычисляется, не хранится**
   - Цель выполнена, когда сумма страниц за сегодня >= `target`. Флаг выполнения не храним: состояние выводится из `read_stats`.
   - Поздравление ровно одно в день: при обновлении прогресса с положительной дельтой `delta`, если `до = сегодня_после_обновления - delta < target <= сегодня_после_обновления`. Повторные обновления в тот же день порог уже не пересекают.
   - Альтернатива: хранить флаг «выполнена» в таблице — отвергнута, избыточно и рассинхронизируется с правками истории.

6. **UX команды `/goal`**
   - `/goal` без аргументов открывает меню: кнопки «Просмотр», «Установить», «Отключить», «Отмена». Быстрого пути `/goal 50` нет — число вводится внутри сценария установки.
   - После любого действия сценарий закрывается: подтверждение + главная клавиатура + `delete_state()` (как в остальных сценариях).
   - «Установить»: ввод целого числа; `>= 1` — установить; `0` — отключить; остальное (не число, отрицательное) — ошибка с подсказкой, клавиатура «Отмена».
   - «Просмотр»: экран «Цель на день: N стр. / Сегодня: X стр. (Z%) / Осталось: M стр.» или «Выполнена»; без цели — «Цель не установлена».
   - Алиасы: `/goal`, `goal`, `цель` (паттерн существующих обработчиков).

7. **Не перехватывать чужие сценарии**
   - В начале `handle()`: если `context.is_active()` и `state_info["command"] != "/goal"` — вернуть `None`. Тогда роутер вторым проходом по `command_state` отдаст сообщение активному сценарию. Исключение — системные команды (`CancelHandler`, priority 100).
   - Механизм зафиксирован в `AGENTS.md` (в существующих обработчиках реализован в `progress.py`, `edit.py`, `details.py`).

8. **Точка интеграции прогресса цели — `ProgressUpdateFlow._finish_progress_update`**
   - Оба пути обновления прогресса (`/progress` и `/edit`) проходят через этот флоу, поэтому строка о цели появится везде.
   - Если цели нет — сообщение не меняется. Если есть: строка `Цель на день: X/Y стр.` (без эмодзи) в обоих вариантах финала (изменён и не изменён прогресс); при пересечении порога — поздравление `🎉 Цель на день выполнена! Сегодня прочитано X из Y страниц.` (вместо обычной строки).
   - Дельта для проверки пересечения известна во флоу (`new_page - current_page` до обновления); `GoalService` даёт `target` и `today_pages`.

## Risks / Trade-offs

- **[Серверное время]** Цель перещёлкивается по часовому поясу сервера, а не пользователя. → Заведён отдельный issue про часовые пояса; поведение задокументировано.
- **[Записи статистики с NULL user_id]** Страницы из книг, удалённых до миграции, не учитываются в сумме дня. → Приемлемо: затрагивает только давно удалённые книги.
- **[Поздравление при нескольких обновлениях]** Возможен пропуск поздравления, если пользователь обновил прогресс путём, не проходящим через `ProgressUpdateFlow`. → Сейчас такого пути нет (весь прогресс идёт через флоу); проверка зафиксирована тестом.
- **[Рост таблицы]** Каждая установка цели — новая строка. → UPSERT по `(user_id, kind)` не даёт таблице расти.

## Migration Plan

- `src/core/migrations.py`: `add_read_stats_user_id(conn)` — идемпотентно (проверка `PRAGMA table_info(read_stats)`), затем `UPDATE ... SET user_id = ...` для NULL-строк. Вызывается в `Database.__init__` рядом с `add_link_column`.
- Таблица `goals` создаётся в `_create_tables` (`CREATE TABLE IF NOT EXISTS`), для существующих баз подхватывается при старте.
- Откат: удаление таблицы `goals` и колонки не требуется для отката кода (код просто не использует их); при необходимости — `DROP TABLE goals` вручную.
