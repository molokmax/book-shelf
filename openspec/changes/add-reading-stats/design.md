## Context

В проекте уже есть полноценная инфраструктура статистики чтения:

- Таблица `read_stats` (`book_id`, `pages_read`, `read_date`), в которую `BookService.update_book_progress` записывает количество новых страниц при каждом обновлении прогресса.
- `ReadingStatsService` с методами `get_reading_stats(book_id, from_date, to_date)`, `avg_pages_per_day(book)` (среднее за 30 дней), `predict_completion_date(book)` (прогноз даты завершения).
- Команда `details` уже выводит недельную/месячную статистику, среднее за 30 дней и прогноз через `helpers.format_book_details`.

Единственная точка, где статистика не показывается, — подтверждение обновления прогресса в `EditHandler._handle_waiting_for_progress_input` (строки `edit.py:663-675`): сообщение содержит только «Прочитано X из Y страниц».

Запись в `read_stats` происходит до формирования ответа (внутри `update_book_progress`), поэтому статистика в ответе уже учитывает только что внесённые страницы.

## Goals / Non-Goals

**Goals:**

- После успешного обновления прогресса показывать блок мини-статистики по книге: прогресс в процентах, неделя, месяц, среднее за 30 дней, прогноз завершения.
- Переиспользовать существующий `ReadingStatsService` без изменения схемы БД и модели данных.
- Вынести форматирование блока мини-статистики в общий хелпер, чтобы не дублировать строки из `format_book_details`.

**Non-Goals:**

- Не менять формат и содержимое команды `details`.
- Не добавлять новые поля в таблицы или модели.
- Не менять алгоритмы расчёта среднего и прогноза (они уже согласованы в `details`).
- Не показывать статистику при ошибках ввода (некорректное число, страница вне диапазона).

## Decisions

- **D1: Собрать статистику в `_handle_waiting_for_progress_input` после успешного `update_book_progress`.**
  Повторяет паттерн `details._handle_selecting_book`: вычисление `week_start`/`month_start` от «сегодня», вызовы `get_reading_stats`, `avg_pages_per_day`, `predict_completion_date` по обновлённой книге (`updated_book`).
  *Альтернатива:* метод-сводка в `ReadingStatsService` (например, `get_progress_summary(book) -> dict`), который за один вызов возвращает все метрики. Не выбран, чтобы не менять сервисный слой без необходимости: все нужные методы уже публичные, а выборку дат детали и edit делают одинаково.

- **D2: Новый хелпер `format_progress_stats(book, weekly_pages, monthly_pages, avg_pages, predicted_date) -> str` в `src/utils/helpers.py`.**
  Возвращает многострочный блок со строками в точном порядке из запроса:
  ```
  Прогресс: {current}/{pages} ({percent}%)
  За последнюю неделю прочитано: {weekly} стр.
  За последний месяц прочитано: {monthly} стр.
  Среднее за 30 дней: {avg:.2f} стр/день
  Ожидаемая дата завершения: {date}
  ```
  При `avg == 0` вместо строк о среднем и дате выводится «Недостаточно данных для оценки завершения» (консистентно с `format_book_details`).
  *Альтернатива:* переиспользовать `format_book_details` целиком. Отклонено: он выводит автора, ссылки, даты и эмодзи — для короткого подтверждения это шум, а требуемый набор строк отличается.

- **D3: Сообщение в edit собирается как конкатенация существующего подтверждения и блока из D2.**
  Текущее начало («✅ Прогресс чтения книги '...' обновлён...») сохраняется, блок статистики добавляется после пустой строки. Поведение ошибок ввода не меняется.

## Risks / Trade-offs

- [Прогноз сразу после первого обновления может быть волатильным (среднее считается по одному дню)] → Это ожидаемо: метод `avg_pages_per_day` уже используется в `details` с тем же окном 30 дней; при нулевой статистике выводится сообщение о недостатке данных.
- [Дублирование логики расчёта дат между `details` и `edit`] → Ограничено двумя вызовами; при дальнейшем росте вынести в `ReadingStatsService.get_progress_summary` (зафиксировано в D1 как осознанная альтернатива).
- [Дополнительные SQL-запросы на каждое обновление прогресса] → Три лёгких агрегатных запроса по индексируемой таблице `read_stats`; приемлемо для сценария VK-бота.
