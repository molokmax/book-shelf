## Context

Пользователи хотят видеть статистику прочитанных страниц за последние 7 дней и за месяц. Сейчас в деталях книги отображается лишь общее количество прочитанных страниц и прогресс. Требуется добавить агрегированные данные в представление детали книги и обеспечить их вычисление в базе.

## Goals / Non-Goals

**Goals:**
- Вывести в ответе `book-detail` количество страниц, прочитанных за week и month.
- Предоставить метод `get_reading_stats(book_id, from_date, to_date)` для получения этих цифр.
- Обновить сообщение бота, чтобы показывать новые данные.
- Добавить покрытие тестами всех новых путей.

**Non-Goals:**
- Не изменять текущую логику подсчёта общего количества прочитанных страниц.
- Не реализовывать историческое хранение каждого отдельного чтения (используем уже существующую таблицу `read_stats`).

## Decisions

- **Хранение статистики:** не создавать отдельную таблицу, а рассчитывать показатели на лету с помощью агрегирующего запроса к `read_stats` (поле `pages_read`). Это сохраняет простоту и отсутствие дублирования данных.
- **Интерфейс сервиса:** добавить в `src/core/services.py` функцию `get_reading_stats(book_id: int, from_date: datetime, to_date: datetime) -> int`; она будет использовать параметры `from_date` и `to_date` и возвращать суммарное количество страниц.
- **Изменения в репозитории:** добавить репозиторий `ReadStatsRepository` в `src/core/repository.py` с методом `fetch_reading_stats(book_id: int, from_date: datetime, to_date: datetime)` для выполнения SQL‑запроса `SELECT SUM(pages_read) FROM read_stats WHERE book_id = ? AND read_date > ? AND read_date <= ?`.
- **Обновление обработчика:** в `src/vk_bot/handlers/details.py` добавить вызов сервиса и включить полученные значения в текст сообщения.
- **Тестирование:** в `tests/test_book_detail.py` добавить случаи, проверяющие корректность возврата статистики за 7 и 30 дней, используя фиктивную БД с предзаполненными записями `read_stats`.
- **Логирование:** добавить сообщения уровня DEBUG в новые методы для облегчения диагностики.

## Risks / Trade-offs

- **Производительность:** агрегатный запрос по `read_stats` может стать дорогим при большом количестве записей. Возможные mitigations: индексировать поле `date` и `book_id`.
- **Миграция:** изменения в схеме запросов могут потребовать обновления миграций БД; однако новых столбцов не добавляем, поэтому миграций не требуется.
